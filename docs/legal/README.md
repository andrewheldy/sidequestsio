# docs/legal/ — Developer Reference

This directory is the **single source of truth** for every SideQuests legal document. This README
is the engineering reference for maintaining that system — how documents are versioned, how they
reach the live site, and what to do when the text needs to change. For the *public-facing* changelog
of what changed and when, see [`Legal-Version-History.md`](./Legal-Version-History.md) instead.

## How rendering works

Each rendered document has a thin page component in `src/pages/` (e.g. `PrivacyPolicy.tsx`,
`CommunityGuidelines.tsx`) that does a **static** Vite `?raw` import of its markdown file:

```ts
import content from "../../docs/legal/Privacy-Policy.md?raw";
```

That raw markdown string is passed to the shared `src/components/legal/LegalDocPage.tsx`
component, which renders it with `react-markdown` + `remark-gfm` (tables, strikethrough, etc.),
plus a small set of custom component overrides:

- `h2`/`h3` get an `id` generated by `src/lib/slugify.ts`, so in-page anchor links
  (`#2-how-we-use-your-information`) actually scroll to the right heading.
- `blockquote` renders as a styled callout box (used for "Location data is never stored..." style
  notes).
- Tables render inside a horizontally-scrollable wrapper so they don't break mobile layouts.
- Internal links (`/terms`, `/cookie-preferences`, etc.) render as React Router `Link`s; external
  links get `target="_blank" rel="noopener noreferrer"`.

**Editing the `.md` file *is* editing the live page.** There is no separate content-sync step, no
CMS, and no build-time content pipeline beyond Vite's raw-string import — what's in the file is
what ships.

Routes are registered in `src/App.tsx` alongside the rest of the public marketing routes.

## Versioning

Every document (except this README and `Legal-Version-History.md`) has a header:

```
**Version:** 1.0.0
**Effective Date:** July 7, 2026
**Last Updated:** July 7, 2026
```

- **`Version`** follows `MAJOR.MINOR.PATCH` — see
  [`Legal-Version-History.md` § How Versioning Works](./Legal-Version-History.md#1-how-versioning-works)
  for what bumps which digit.
- **`Effective Date`** is when the current version's actual terms/obligations took (or take)
  effect. It changes on a **minor or major** bump (something a user is agreeing to actually
  changed). A **patch** bump (typos, formatting, contact-detail corrections — no change in
  meaning, e.g. the `support@miamisidequests.io` email consolidation) leaves it as-is; only
  `Last Updated` moves.
- **`Last Updated`** changes any time the file is touched, even for trivial fixes that don't bump
  the version (e.g., fixing a broken link) — it's a "was this file recently reviewed" signal, not a
  legal marker.

These fields live **only** in the markdown header — they are not templated, generated, or pulled
from any other source. There's no dynamic "last modified" date computed from git; whoever edits the
file is responsible for updating the header by hand.

## Where effective dates are updated

Directly in the `.md` file's header, by hand, as part of the same change that edits the document's
body. There is no other place effective dates are stored or derived from for the six rendered
documents.

## How consent versions map to the database

Two of these documents — `Terms-of-Service.md` and `Privacy-Policy.md` — are things users must
actively agree to, and that agreement is recorded in the database with a version stamp. The mapping
works like this:

1. `src/lib/legal.ts` exports `CURRENT_TERMS_VERSION` and `CURRENT_PRIVACY_VERSION` — plain string
   constants (currently both `"1.0.0"`; the documents themselves have since moved to `1.0.1` for a
   contact-email patch — see below for why these constants weren't bumped along with them).
2. At signup, `src/pages/Auth.tsx` requires the user to check "I agree to the Terms of Service and
   Privacy Policy" before submitting. `src/contexts/AuthContext.tsx`'s `signUp()` passes those two
   constants (plus the optional marketing opt-in) into `supabase.auth.signUp()`'s `options.data`
   (stored as `auth.users.raw_user_meta_data`).
3. The `handle_new_auth_user()` trigger (`supabase/migrations/0010_auth_bootstrap.sql`, extended by
   `supabase/migrations/0015_legal_consent.sql`) reads that metadata when it creates the user's
   `public.profiles` row, writing `terms_version`, `privacy_version`, `accepted_terms_at`,
   `accepted_privacy_at`, `marketing_opt_in`, and `marketing_opt_in_at`.

**This means `src/lib/legal.ts`'s constants and each document's `Version:` header must be bumped
together for minor/major changes.** If you change `Terms-of-Service.md` in a way that bumps its
*minor or major* version but forget to bump `CURRENT_TERMS_VERSION` in `src/lib/legal.ts`, new
signups will be stamped with the *old* version number even though they saw the *new* text — the
database record of "what a user agreed to" will silently drift from the truth. Treat these as one
atomic change.

**Patch bumps are the deliberate exception.** `terms_version`/`privacy_version` exist to answer
"what did this user actually agree to" for compliance purposes — a patch (typo fix, formatting,
contact-detail correction; see `Legal-Version-History.md` § How Versioning Works) doesn't change
what anyone agreed to, so it doesn't need a new consent stamp. Example: the `1.0.0` → `1.0.1`
contact-email consolidation (all documents now point to `support@miamisidequests.io`) bumped every
document's header but intentionally left `CURRENT_TERMS_VERSION`/`CURRENT_PRIVACY_VERSION` at
`"1.0.0"` in `src/lib/legal.ts`. If this judgment call ever feels wrong for a specific patch (e.g.
a "typo fix" that arguably does change meaning), bump the constant anyway — when in doubt, a
signup timestamp for a version one patch newer than necessary is harmless; a silently-drifted
consent record is not.

Note that `accepted_terms_at`/`accepted_privacy_at` are captured **once, at signup** — they are not
re-captured automatically when a document's version changes later. See "Process for future
revisions" below for what to consider when that happens.

## Process for future legal revisions

1. Edit the document's body in `docs/legal/*.md`.
2. Bump its `Version:` header (per the semantic rules above) and update `Effective Date:` and
   `Last Updated:`.
3. If the document is `Terms-of-Service.md` or `Privacy-Policy.md`, bump the matching constant in
   `src/lib/legal.ts` in the **same change**.
4. Add a row to [`Legal-Version-History.md`](./Legal-Version-History.md) describing what changed.
5. For a **material** change to Terms or Privacy (a major version bump), decide whether existing
   users need to be re-prompted to accept the new version. This system does not currently implement
   re-prompting for existing users — `accepted_terms_at`/`terms_version` only reflect what a user
   agreed to at signup. Building a re-consent flow (e.g., an in-app banner gating access until
   re-acceptance) is a reasonable future addition once it's actually needed, not something to
   build speculatively now.
6. Run `npx tsc -p tsconfig.app.json --noEmit` and `npm run build` — since the markdown is imported
   as a raw string, most content edits can't break the build, but this is still good practice
   whenever `src/lib/legal.ts` or any page/component in this pipeline changes.

## Things intentionally *not* built here

- No CMS or admin UI for editing legal text — these are markdown files reviewed and edited like any
  other code change (PR review, git history as the audit trail).
- No automatic re-consent flow when a document version bumps (see step 5 above).
- No translation of document bodies — the six rendered documents are English-only, even though the
  rest of the marketing site is bilingual (see `src/i18n/`). Only the *footer link labels* pointing
  to these documents are translated.
